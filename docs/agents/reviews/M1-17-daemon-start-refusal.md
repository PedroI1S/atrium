# Review: M1-17-daemon-start-refusal (N9; D-091, D-094)

Reviewer: Sonnet 5.5 (read-only). Branch `agent/hydrogen/M1-17-daemon-start-refusal`, tip 4038fb5. Author: Gemini 4 Hydrogen medium.

## Verdict: approve with changes

Toolchain is green, owned paths respected, no UI or wire change, the `unsafe` block is untouched (moved into `detached_command`, same text). The mechanism works and the three tests fail without the fix. Two things need a decision before merge: a transient start failure now parks the client in `Failed` (F1), and the handoff's diagnosis is partly wrong about where the silence came from (F2).

## Findings

| # | Sev. | Where | Finding |
|---|---|---|---|
| F1 | major | `crates/atrium-client/src/connection.rs:144-163`; `crates/atrium-host/src/lifecycle.rs:336-366` | **A start that races another daemon now sticks in `Failed`.** The client calls `start_daemon` whenever the socket is missing. If a daemon is already starting (a launchd/systemd keep-running service at login, a second app window, an app relaunch), it holds the lock but has not bound the socket yet. The second `atriumd` exits with "another daemon is already running", `spawn_detached_wait` returns that as `Err`, the client sets `Failed` and waits for Reconnect/Shutdown. Before, it retried and connected a few ms later. Now the banner shows a refusal until the user clicks "Try again", even though the first daemon came up. The new `held_instance_lock` test asserts exactly this outcome, so it cannot catch it. Fix: treat `AlreadyRunning` as "keep retrying" (not a failure), or after `Failed` keep the backoff loop running (keep retrying quietly, replace the message when it connects). Same shape for any other transient `start()` error (executable briefly missing during an app update). |
| F2 | minor | handoff "Where the reason was lost" item 3; `crates/atrium-daemon/src/lib.rs:298` | **On dev the daemon does not refuse a 0755 `logs` folder.** I ran dev's `atriumd` with `ATRIUM_HOME` set and `logs` at 0755: it starts and stays up, stderr empty. The silence N9 saw came from the launcher: `open_private_log` (and the app hook's `secure_dir`) refused, and the client discarded the `Err`, so no daemon was ever started. The worker's new `secure_dir(&paths.logs_dir)` in `Daemon::start` is therefore a new refusal, not a fix of a silent one. It is consistent with the brief and harmless for the app path (the old hook already ran `secure_dir` on that folder, so an install that worked still passes; launchd/systemd starts never wrote there, so a 0755 `logs` folder, if one exists, would now stop a service-started daemon that doesn't use it). Ask: keep it (D-091 text says "any LifecycleError from secure_dir") or drop it. Handoff should state the real cause. |
| F3 | minor | `lifecycle.rs:368-390` | In the log-unopenable branch the loop never checks `ready`, so a daemon that comes up healthy is killed at the deadline and the user gets the log-open error. Right call by the brief's rule (no daemon without a private log) and it costs nothing when the log is fine, but the message should say the daemon was stopped, and the loop could stop early on `ready.exists()` to kill sooner. If `try_wait()?` errors, the child is leaked (negligible). |
| F4 | minor | `lifecycle.rs:404-423`, `tail_lines` (up to 5 lines) | Brief says one line. Daemon-side refusals are one line (tests assert it); what reaches the client is the last up to 5 lines of the log or stderr, so a panic backtrace or a chatty log could put several lines, and anything the daemon printed, into the banner. No secrets found in the refusal messages (paths and modes only). Consider showing only the last line, or capping to the refusal lines. |
| F5 | minor | `crates/atrium-daemon/tests/start_refusal.rs` | The 0755 and symlink client tests run with `default_paths()` not matching the temp folder, so `open_private_log` opens the log fine and the log-tail path is the one exercised. The real app case (default `logs_dir` is 0755, `open_private_log` refuses, stderr pipe fallback) is only covered by the `/bin/sh` unit test in `tests/lifecycle.rs`, not with the real daemon. Acceptable; say so in the handoff. |
| F6 | nit | `lifecycle.rs:336-340` | `start_offset` is read after open with `O_APPEND`; if another process appends between that read and spawn, its lines are not shown, or an unrelated line could be. Negligible. |

## Answers to the review questions

1. **Toolchain** (4038fb5): `cargo fmt --all --check` ok; `cargo clippy --workspace --all-targets -- -D warnings` ok; `cargo test -p atrium-host -p atrium-daemon -p atrium-client -p atrium-app` all pass (client 28+11, daemon 15+1+2+2+3+6+2+19+9+3, host 5+5+3+9, app 45+2); `scripts/check-protocol-ts` up to date; app `pnpm typecheck` ok, `pnpm test` 264 passed. No wire or TS change. `ConnectionBanner.tsx` already renders `failed` with `s.message` and a "Try again" button (calls `reconnect`), so no new UI.
2. **Diagnosis:** two of three parts are right (client discarded the `Result`; `spawn_detached` neither waited nor piped stderr). The third (daemon silently refusing logs) is not what happened on dev, see F2. The new `secure_dir(logs_dir)` does not change a correct install: the app hook already secured that folder with the same check, created 0700. Risk is limited to a logs folder with another mode or owner that only a service-started daemon met (F2).
3. **`spawn_detached_wait`:** returns as soon as `ready` (the socket) exists or the child exits, so a healthy start does not pay 500 ms (a stale socket file makes it return at once, as before). Only a daemon that is slow to bind waits the full 500 ms, then `Ok`. Kill on "alive without private log": right under the brief, see F3. `unsafe pre_exec` text unchanged, now in `detached_command`. Children: reaped by `try_wait` on exit, by `wait` after kill, or by `reap_in_background`; no zombie or fd leak found. After a daemon that ran with the stderr pipe is killed there is no reader left, fine.
4. **Pause after Failed:** correct when the cause is permanent and the user can click "Try again" (the banner has it; the app also calls `reconnect` on upgrade). Wrong for transient causes (F1): previously the loop recovered on its own. After the user fixes a folder mode, "Try again" restarts at attempt 0 and works. Not automatic.
5. **Messages:** name folder, state and expectation ("permissions 0755, expected 0700", "directory is a symlink, expected a 0700 directory", lock: pid and "expected only one instance"). Tests use temp folders only; no real home path. See F4 for line count.
6. **Tests against dev's code:** with dev's `connection.rs` swapped in, all three `start_refusal` tests fail (no `Failed`, panic at `wait_for_failed`). With dev's `lib.rs` the daemon starts and stays up on a 0755 logs folder (so the daemon-side half of the 0755 test would also fail). The `lifecycle` test and the helper do not compile on dev (`spawn_detached_wait` is new). Restored afterwards.
7. **Owned paths:** all seven changed files are in the brief's list (host lifecycle + test, daemon lib.rs one line + new test, client connection.rs, bridge.rs, handoff). The brief listed `crates/atrium-client/src/lib.rs`; the change is in `connection.rs`, same crate, start-up error path only. `lib.rs` of the app untouched.
8. **Trial merge of dev (e4e869b):** merged cleanly, no conflicts; `cargo fmt` ok, `cargo clippy --workspace --all-targets -D warnings` ok, host/daemon/client tests all pass. (App tests and pnpm not re-run on the merge; dev's changes are agents/host supervise only.)
