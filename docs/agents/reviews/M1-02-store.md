# Review: M1-02-store
Reviewer: Gemini 4 Argon (read-only) · 2026-11-09

## Verdict
**approve with changes** — The store's transactional projections, `RequestStore` status isolation, restart SHA-256 recovery, migration rollback, read-only exemptions, and 3M-token memory footprint (14.1 MiB `phys_footprint` / 18.4 MiB RSS) are solid, needing targeted fixes for cross-incarnation pending counters, bounded async queueing, and `O_NOFOLLOW` symlink-safe path handling.

## Findings

1. **[major] `begin_incarnation` carries unclosed `pending_approvals` and `pending_questions` into the new incarnation, corrupting `ThreadState` and attention fields**
   - **Where:** `crates/atrium-core/src/store/writer.rs:311-329`, `crates/atrium-core/src/store/writer.rs:154-170`, `crates/atrium-core/tests/store.rs:840-898`
   - **Problem:** `Writer::begin_incarnation` advances `threads.incarnation` without resetting `threads.pending_approvals` and `threads.pending_questions`. If a previous incarnation ended without `RequestResolved` for an open request, its count leaks into the new incarnation. This actually happens in `incarnations_scope_sequences_and_requests` (`tests/store.rs:820-898`): incarnation 1 leaves `r1` unclosed (`pa = 1`), incarnation 2 opens `r1` (`pa = 2`) and resolves `r1` (`pa = 1`), leaving `summary.pending_approvals == 1`, `summary.state == ThreadState::NeedsApproval`, and `(attention_since_ms, attention_detail) == (Some(1003), None)` (from the fallback branch in `oldest` at `writer.rs:169`) even though incarnation 2 has zero open requests (`open_items(&t, 2).requests` is empty). The test missed it because lines 894–898 only assert `(s.incarnation, s.native_session_id)`.
   - **Fix:** In `Writer::begin_incarnation`, reset `pending_approvals = 0` and `pending_questions = 0` on `threads` and recompute `refresh_attention` / `save_row` inside the same `IMMEDIATE` transaction (clearing stale `Approval`/`Question` attention while keeping sticky `Failed`/`Cleanup::Unverified`/`Reply` until `Signal::Starting`). Assert `s.pending_approvals == 0` and `s.state == ThreadState::Running` after incarnation 2 resolves `r1` in `incarnations_scope_sequences_and_requests`.

2. **[major] Async-to-writer job queue is unbounded (`std::sync::mpsc::channel`), and `Shared::read` parks Tokio blocking-pool threads on a `Condvar`**
   - **Where:** `crates/atrium-core/src/store/mod.rs:18, 72, 99-134, 232`, `crates/atrium-core/src/store/reader.rs:18-21, 42-61`
   - **Problem:** `SqliteStore::open_blocking` connects callers to `atrium-store-writer` with an unbounded `std::sync::mpsc::channel::<Job>()` (`mod.rs:232`), and `Shared::call` enqueues synchronously without awaiting capacity (`mod.rs:112-117`). Under slow `fsync`/WAL checkpoints or concurrent appends carrying multi-megabyte `Vec<AgentEventEnvelope>` batches, callers receive no async backpressure and queued batches can grow without bound. On the read side, `Shared::read` (`mod.rs:128-133`) spawns a `tokio::task::spawn_blocking` OS task on every call before acquiring one of the `limits::STORE_READERS` (`2`) connections, parking excess blocking-pool threads on `Condvar::wait` (`reader.rs:48-51`) — e.g. while `snapshot` holds one reader connection during `VACUUM INTO`.
   - **Fix:** Replace `std::sync::mpsc::channel` with a bounded `tokio::sync::mpsc::channel::<Job>(cap)` (cloning the sender before `.send(job).await` without holding a `std::sync::Mutex` across `.await`, and looping on `rx.blocking_recv()` on the writer thread; no deadlock is possible because `Writer` never calls back into `Shared::call` or `Shared::read`). Gate `ReaderPool` with a `tokio::sync::Semaphore` of `limits::STORE_READERS` permits acquired in async context before `tokio::task::spawn_blocking`.

3. **[major] Database and snapshot creation omit `O_NOFOLLOW` and symlink checks (`set_permissions` follows symlinked snapshot dirs; existing DB modes stay loose)**
   - **Where:** `crates/atrium-core/src/store/mod.rs:208-214`, `crates/atrium-core/src/store/snapshot.rs:78-96`
   - **Problem:** `SqliteStore::open_blocking` opens `path` via `OpenOptions::new().create(true).append(true).mode(0o600).open(&path)` without `O_NOFOLLOW`, without checking `<path>-wal` / `<path>-shm` / `<path>-journal` for symlinks, and without tightening permissions on pre-existing files (`mode(0o600)` only applies on creation, leaving an existing `0644` file `0644`). If `path` is a symlink (existing or dangling), `open` follows it. Similarly, `snapshot::snapshot` calls `std::fs::create_dir_all(&target)` (using process `umask`) followed by path-based `std::fs::set_permissions(&target, 0o700)` (`snapshot.rs:78-79`), which follows a symlinked `target` directory and `chmod 0700`s its destination, and omits `O_NOFOLLOW` when creating `p`.
   - **Fix:** Open `path` with `O_NOFOLLOW` (`OpenOptionsExt::custom_flags(rustix::fs::OFlags::NOFOLLOW.bits() as i32)` — `rustix` with `fs` is already in `Cargo.toml`), verify regular-file ownership via `Metadata` on the opened `File`, tighten mode to `0o600` via `File::set_permissions` (`fchmod`, which does not modify file bytes), and reject symlinked `-wal`/`-shm`/`-journal` sidecars via `symlink_metadata`. In `snapshot.rs`, create `target` with `DirBuilder::new().recursive(true).mode(0o700)`, verify `symlink_metadata(&target)` is a non-symlink directory owned by the current uid with mode `0700`, and pass `O_NOFOLLOW` when opening `p`. Add symlink rejection tests for both `open` and `snapshot`.

4. **[minor] `Store::rules()` executes two `SELECT` statements outside a transaction and can return a torn `(revision, rules)` snapshot**
   - **Where:** `crates/atrium-core/src/store/reader.rs:139-157`
   - **Problem:** `reader::rules` runs `SELECT revision FROM rules_revision WHERE id = 1` in autocommit mode and then runs `SELECT rule FROM rules ORDER BY created_ms, rowid` as a second autocommit query. If `create_rule`, `delete_rule`, or `approve_with_rule` commits on the writer thread between the two statements, `rules()` returns the old `revision` paired with the new `Vec<Rule>` — a state that never existed, which can poison a revision-keyed rules cache or mispair `PolicyContext.rules_revision` in `SessionGate`.
   - **Fix:** Wrap the two queries in `let tx = c.unchecked_transaction().map_err(sql_err)?;` (`BEGIN DEFERRED`) so both `SELECT`s read from the same WAL snapshot.

5. **[minor] Panics caught on `atrium-store-writer` roll back SQLite via `Drop` but leave `Writer.hashers` mutated**
   - **Where:** `crates/atrium-core/src/store/mod.rs:237-242`, `crates/atrium-core/src/store/writer.rs:405-410, 454-471`
   - **Problem:** `atrium-store-writer` catches panics with `catch_unwind(AssertUnwindSafe(|| job(&mut writer)))` and continues serving jobs on `writer`. Inside `append_tx`, `apply` mutates `writer.hashers` in place (`writer.rs:454`) before `(opts.transition)(...)` runs (`writer.rs:464` — notably `StoreOptions::default().transition` is `attention::next_state`, currently `unimplemented!("M1-04")`). Unwinding drops `rusqlite::Transaction` (rolling back `events` and `open_messages`) while bypassing `if out.is_err() { self.hashers.retain(...); }` (`writer.rs:406-410`), leaving `writer.hashers` ahead of committed deltas and causing wrong `open_items` hashes and false `MessageCompleted` integrity errors on later calls.
   - **Fix:** On `Err(_)` from `catch_unwind` (or via a rollback guard inside `append_tx` disarmed only after `tx.commit()`), clear `writer.hashers` so `ensure_hasher` recomputes from committed `events` on next use, and execute `ROLLBACK` if `!writer.conn.is_autocommit()`.

6. **[minor] `ApprovalRequested` mutates `requests.title` when `Binding.title` is `None`, altering `RequestStore::binding`**
   - **Where:** `crates/atrium-core/src/store/writer.rs:157, 854-877`
   - **Problem:** Contract §5 and §7 (`docs/contracts/m1.md:119`, `crates/atrium-core/src/lib.rs:316-319`, `docs/agents/briefs/M1-02-store.md:29`) specify that `Store::append` marks `event_opened = 1` on `ApprovalRequested`/`QuestionAsked` and sets `title` only on `QuestionAsked` (whose `open_question` has no `Binding`). In `writer.rs:862-872`, `ApprovalRequested` runs `UPDATE requests SET event_opened = 1, title = COALESCE(title, ?4)` with `title.clone().unwrap_or_else(|| name.clone())`. When `RequestStore::open_approval` was called with `Binding { title: None, .. }`, storing `ApprovalRequested` overwrites `requests.title` with `Some(...)` (even when `ApprovalRequested.title` is also `None`), so `RequestStore::binding(&key)` no longer round-trips the `Binding` opened by the ledger; `oldest` (`writer.rs:157`) likewise substitutes `tool_name` via `COALESCE(title, tool_name)` instead of keeping `attention_detail` as the approval's `title` (`None`).
   - **Fix:** Update only `SET event_opened = 1` on `ApprovalRequested` in `writer.rs:862`, select `title, opened_ms` directly in `writer.rs:157`, and extend `store_never_changes_request_status` to cover `Binding { title: None, .. }`.

7. **[minor] `events_after` casts `after: u64` and `limit: usize` directly `as i64`, wrapping large values negative**
   - **Where:** `crates/atrium-core/src/store/reader.rs:76-81`
   - **Problem:** `EventId(pub u64)` is deserialized from client `Subscribe` messages. Any `after` above `i64::MAX as u64` (e.g. `EventId(u64::MAX)`) wraps to a negative `i64` (`-1`), making `event_id > ?2` replay the entire thread from event 1 instead of returning an empty page; any `limit > i64::MAX as usize` wraps negative, which SQLite treats as `LIMIT -1` (unlimited).
   - **Fix:** Clamp both parameters with `i64::try_from(e.0).unwrap_or(i64::MAX)` and `i64::try_from(limit).unwrap_or(i64::MAX)` (and short-circuit `limit == 0`).

8. **[minor] `statvfs_free` fails open (`u64::MAX`) when `statvfs` errors, and test suite omits `Usage`, `EnforcementChanged`/`set_enforcement`, and multi-approval ordering**
   - **Where:** `crates/atrium-core/src/store/mod.rs:166-171, 198-205`, `crates/atrium-core/tests/store.rs`
   - **Problem:** When using `StoreOptions::default()`, `statvfs_free` returns `u64::MAX` on `Err(_)` (`mod.rs:169`), reporting unlimited free space instead of failing closed into `ReadOnly` if `statvfs` fails (e.g. `EIO`, or a relative `path` whose `dir` is `"."` after a cwd change). In `tests/store.rs`, `AgentEvent::Usage` / `TurnCompleted.usage` (`turns.usage`), `AgentEvent::EnforcementChanged` / `Store::set_enforcement`, oldest-first `attention_detail` across two concurrent open approvals, and `ReadOnly` rejection of `approve_with_rule` and `snapshot` have no test coverage.
   - **Fix:** Canonicalize `dir` in `open_blocking` and return `0` on `Err(_)` in `statvfs_free`; add tests in `crates/atrium-core/tests/store.rs` covering `Usage`/`TurnCompleted.usage`, `EnforcementChanged`/`set_enforcement`, two concurrent open approvals (verifying oldest wins and resolving it shifts `attention_detail` to the next), and `approve_with_rule`/`snapshot` under `ReadOnly`.

9. **[nit] `Cargo.lock` modified outside owned paths and `pub use migrate::Migration` lacks `#[doc(hidden)]`**
   - **Where:** `Cargo.lock`, `crates/atrium-core/src/store/mod.rs:39`
   - **Problem:** Contract §2 (`docs/contracts/m1.md:49`) reserves `Cargo.lock` for the orchestrator and `docs/agents/briefs/M1-02-store.md:17-21` excludes it from owned paths, so committing `Cargo.lock` changes will conflict at Wave 1 integration. Also, `pub use migrate::Migration;` (`mod.rs:39`) is exposed in public docs without `#[doc(hidden)]`, whereas its only consumer `SqliteStore::open_with` (`mod.rs:181`) is `#[doc(hidden)]` (none of the added public items — `Default for StoreOptions`, `integrity_errors`, `open_with`, `Migration` — weaken any security or contract boundary).
   - **Fix:** Revert `Cargo.lock` to `0fba94e` before merge (leaving lockfile resolution to the orchestrator) and add `#[doc(hidden)]` to `pub use migrate::Migration;`.
