## 3. Enforcement per session (G1, D-044)

- `AgentAdapter::interception()` is gone. `AgentAdapter::probe(&SessionConfig)` returns the `EnforcementDescriptor` a session would get, for the provider picker. `Session::descriptor` and `AgentEvent::SessionStarted.enforcement` carry the one it actually got. If something changes mid-session (a hook appears, the gate becomes unreachable), the adapter emits `EnforcementChanged`.
- **Full** only when every tool class in `ToolClass::ALL` is `Coverage::Intercepted` or `NotApplicable` (the weakest entry counts when a class has several), the CLI version is known and in the adapter's `tested_versions()`, and every configuration source the provider loads was inspected. Anything else is **Partial** with at least one `EnforcementReason`. There is no third level; unknown coverage is Partial.
- Configuration provenance is part of the descriptor: every settings file, plugin directory and managed policy the adapter found, with a content hash. Claude plugin hooks, `--settings` and `--plugin-dir` files, `enabledPlugins`, and any existing file the adapter can't read or parse count as uninspected. Settings keys that run commands (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `otelHeadersHelper`, `statusLine`, hooks) add an `ExternalHooks` reason.
- `DaemonCommand::ProbeProviders` runs `probe` for every provider, for the provider picker and *Settings → Agents*.
- Wording in the UI and in PLAN §3.12 keeps three things apart:
  - **coverage**: which calls Atrium sees before they run;
  - **policy**: what Atrium does with them (rules, presets, the deny list);
  - **isolation**: what limits code that was allowed to run. Only the sandbox (M4) gives that.
- The deny list is shown as **"Always blocked (for calls Atrium sees)"**. No UI text says or implies that a command is impossible.

## 4. Daemon authority (G2, D-045)

- A connection's role is fixed at `Hello` and never changes. The daemon answers `Welcome { role }` with the role it granted, or `Incompatible` and closes.
- `ClientRole::App`: granted only after **peer verification** (`atrium_host::peer`):
  - macOS (11 or later): the peer's audit token (`LOCAL_PEERTOKEN`) → `SecCodeCopyGuestWithAttributes` with `kSecGuestAttributeAudit` (CR-05) → `SecCodeCheckValidity` against the app's designated requirement (bundle id + team id), **compiled into release daemons**. Unsigned development builds compare the running (dynamic) code object's cdhash (`kSecCodeInfoUnique`, never the static code on disk or a hash of the file) with `Paths::app_identity`, written by the dev app (mode 0600, owner checked).
  - Linux: `SO_PEERCRED` → pid, the peer's pidfd from `SO_PEERPIDFD` (kernel 6.5+; without it App authority is refused, since a `pidfd_open` fallback races with pid reuse), `/proc/<pid>/exe` must be the packaged app path compiled into release daemons, which the daemon checks at runtime is owned by root and not writable by the user (development identities also pin device + inode), then `pidfd_send_signal(pidfd, 0)` to prove the inspected process is still the one connected.
  - The uid is checked first.
  - Failure of any step → `Incompatible { message: "unverified client" }`. Never a downgrade to a lesser role.
- `ClientRole::Dev`: for tests and harnesses. Accepted only when the daemon was started with `--dev-socket` **and** is a debug build. Release builds reject it. Dev has App authority.
- `ClientRole::Agent { token }`: reserved for the MCP server (later milestone). M1 daemons reject it.
- Every `DaemonCommand` declares the authority it needs (`DaemonCommand::authority()`), and the daemon checks it before doing anything. In M1, every command needs `App`; the table exists so later roles cannot silently gain human-control commands.
- The remaining limit, stated in PLAN §3.1 and in Settings → Security: an unconfined agent running as your user can do anything you can, including modifying Atrium's files. Peer verification raises the bar; it is not isolation.

## 5. Approvals (G3, D-046)

- **One authority.** `atrium-core::ApprovalLedger` owns every approval and question and is the **only writer** of `requests.status`. Event appends never change it; a stored `RequestResolved` only marks the row's event as closed (`event_closed`), which is what crash recovery uses to know what to close. States: `pending → approved → redeemed`; `pending → denied | answered | cancelled | expired`; `approved → cancelled | expired`.
- **Driven by events.** After storing them, the daemon calls the ledger: `RequestResolved { cancelled | expired }` → `withdraw`; `TurnCompleted` → `expire_turn`; `SessionEnded` → `expire_incarnation`.
- **Limit.** The ledger refuses to open more than `limits::MAX_PENDING_REQUESTS` pending or approved requests per incarnation (the gate then denies), so no hidden rows are left behind.
- **Tickets.** When the gate answers `Ask`, it opens a ledger entry and returns `GateDecision::Ask { ticket }`. The adapter uses `ticket.request_id` as the `ApprovalRequested.request_id`; provider-native ids stay inside the adapter.
- **Binding.** An entry is bound to: thread, session incarnation, turn (the adapter's own counter, carried in `ToolCheck.turn`, so it never races the event stream), request id, tool name, tool kind, the SHA-256 of the canonical input (`policy::canonical_input`), the policy context (rules revision and preset), and the "always…" matcher the gate computed (`Binding::remember_matcher`; `ApprovalRequested.rememberable` tells the UI whether to offer "always…").
- **Questions** get tickets too (`ToolGate::question_ticket(turn)`), recorded as `AdapterInput::QuestionTicket` so replays are deterministic.
- **Resolve.** `ResolveApproval` from an App connection goes to the ledger first. The ledger rejects it (and the client shows "expired") when the entry is unknown, already resolved, expired, or belongs to an older incarnation. Only an accepted resolution is forwarded to the session.
- **Redeem.** Before the adapter performs the effect (answering the provider's control request, writing a file for ACP, retrying for `agy`), it calls `ToolGate::redeem(ticket, &check)` with a check built from the provider's own request at that moment. Redeem consumes the grant exactly once, requires the same turn and canonical input as the binding, and, if the rules or preset changed since the approval, re-evaluates the policy and refuses when it now denies (a deny rule added meanwhile wins; the rule created by this approval's own "always…" doesn't count as a change against it). Anything else returns `Deny`. No I/O happens on any path that didn't redeem successfully.
- **Lifetime.** Entries never auto-allow. They expire when the turn ends, the session ends, the incarnation is replaced, the daemon restarts, or the provider withdraws or times out the request. At startup the daemon first stores the closing events of every incarnation that was live (from `Store::open_items`), then expires every pending or approved entry, all before accepting clients or starting sessions. A ledger row whose `ApprovalRequested`/`QuestionAsked` never got stored (a crash in between) is expired without any event: the store tracks `event_opened` as well as `event_closed`, and only rows with both an opening and no closing event are closed with a `RequestResolved`.
- **Stale keys.** The ledger compares a key's incarnation with `RequestStore::current_incarnation` and answers `StaleIncarnation` for an older one.
- **Remember.** `ResolveApproval { remember: Some(scope) }` with `Allow` also creates a rule (PLAN §3.12: this thread / Home / always), from the binding's `remember_matcher`. The rule is created in the same transaction as the resolution, only if the request was still `pending`, and applies from the next check on; it never re-authorizes a request that already expired. Only literal requests are rememberable: one simple command with no assignments, harmless redirects only and no `$`, globs or braces (→ `CommandExact` of its whole argv, so extra arguments ask again; CR-06, D-054), or a file tool with exactly one path (→ `PathGlob` of the resolved path, glob metacharacters escaped).
- **Hard deny wins** over every rule and every remembered decision, for calls the gate sees. A hard-denied call is never turned into an `Ask`.

## 6. Protocol changes (G4)

### 6.1 Agent events (`agent.rs`)

- **Incarnations.** A thread runs one provider session at a time. Each start or resume of a provider process is a new incarnation (`u32`, from 1, per thread). The envelope carries it. Sequences, turn numbers and request ids are scoped to `(thread, incarnation)`.
- **Messages (CR-03, amended).** `MessageCompleted.body` is `MessageBody::Streamed { chars, deltas, sha256 }` whenever deltas were emitted, and `MessageBody::Inline { text }` only for a completion-only message of at most `limits::MAX_INLINE_MESSAGE_BYTES`. A completion-only message larger than that is split by the adapter into deltas first, so it is always `Streamed`. There is **no** older-client fallback: the app and daemon ship together, and a version mismatch is `Incompatible`. The store keeps a message's deltas as long as its completion. A `chars`/`sha256` mismatch is a hard error at reconstruction, never patched.
- **User messages.** Each turn's user message is stored as a `MessageKind::User` message, emitted by the adapter right after `TurnStarted` (after `SessionStarted` for providers that start lazily) from the `SendUserMessage` it sent, with the same inline/delta rules. Replay, pop-outs, scrollback paging and export see the whole conversation. User messages never set `unread`.
- **Enforcement in fixtures.** The adapter records the descriptor it built as `AdapterInput::Enforcement`, so offline replay emits the same `SessionStarted.enforcement` and `EnforcementChanged`. The sanitizer cleans every `ToolCheck` subject and the descriptor's paths and messages.
- **Context occupancy.** `ContextUpdated { used_tokens, window_tokens }` is separate from `Usage`. ACP's `UsageUpdate.used` and Claude's context figures go here, not into `input_tokens`.
- **Unmapped records** keep at most `limits::MAX_UNMAPPED_RAW_BYTES` of `raw`.
- **Pre-session diagnostics.** `Error` gains `details: Vec<String>` (stderr tail, unparsed startup records, each line at most `limits::MAX_DIAGNOSTIC_LINE_BYTES`, at most `limits::MAX_DIAGNOSTIC_LINES`). A pre-session failure is still exactly `Error { fatal: true }` then `SessionEnded`: no `Unmapped` events before `SessionStarted` (X6).
- **Bounded output.** `ToolCallUpdated.output_delta` and `ToolCallFinished.output` are capped per call at `limits::MAX_TOOL_OUTPUT_BYTES` total; beyond that the adapter emits one `truncated` marker (`ToolCallFinished.truncated_bytes`) and drops the rest. Provider records above `limits::MAX_PROVIDER_RECORD_BYTES` end the session with a fatal `Error`.

### 6.2 Wire (`wire.rs`)

- `PROTOCOL_VERSION` = 1.
- Two lanes per connection: **control** (responses, `ThreadUpdated`, inbox updates) is always written before **replay** pages and live events. A command is never stuck behind replay.
- Each connection has an outbound byte budget (`limits::MAX_CONNECTION_QUEUE_BYTES`). When a subscription would exceed it, the daemon drops **that subscription** and sends `SubscriptionLagged { thread_id, last_sent }`; the client resubscribes from its applied cursor. Other subscriptions and the control lane are unaffected.
- Quotas: `MAX_CONNECTIONS`, `MAX_SUBSCRIPTIONS_PER_CONNECTION`, `MAX_CLIENT_FRAME_LEN` (client → daemon frames are much smaller than daemon → client ones), a deadline for `Hello` (`HELLO_TIMEOUT`).
- `CommandResult::Err` carries an `ErrorCode` clients branch on (`Expired`, `UnknownThread`, `NotRunning`, `StorageReadOnly`, `TurnsRunning`, `Forbidden`, `Invalid`, `Internal`).
- `SubscribeInbox` answers with the full current set (threads and inbox) in its response, then streams changes. A thread that is archived leaves the list with `ThreadRemoved { thread_id }`, sent to every inbox subscriber (CR-07, D-058).
- **Replaced subscriptions (CR-07, D-058).** Once the daemon has answered a `Subscribe` or processed an `Unsubscribe`, it sends nothing of an earlier subscription to that thread on that connection, queued frames included. `ReplayDone.last` equals the response's `replay_until`. A cursor beyond the thread's last event is answered with `Invalid`, an unknown thread with `UnknownThread`.
- `CreateRule` takes a `RuleDraft`; the daemon assigns the id, origin and time. `RenameThread` (`Store::rename`) and `ProbeProviders` are added.
- `AgentLaunch::Native { provider, model, effort, preset }` replaces the M0 placeholder. MCP servers are daemon-owned and never come from the client. Resume is its own command (`ResumeThread`), since it reuses a thread.

## 7. Store (`atrium-core::store`)

- SQLite, WAL, `synchronous = NORMAL`, one writer task. Reads go through a small pool of read-only connections (X4: no per-connection page caches beyond `limits::SQLITE_CACHE_KIB`).
- **Atomic append.** Appending an event updates every projection it touches (thread state and attention fields, turn, open messages, open tool calls, the request's `event_opened`/`event_closed` and a question's title, usage) in the same transaction. A batch for an incarnation that is no longer current is rejected. Closing a thread never folds its full history (gate review, L8): the closing events come from the projections of what is still open. Each open message's running SHA-256 lives in the writer's memory and is recomputed from its stored deltas after a crash.
- **Quotas and disk-full.** Per-event payload ≤ `limits::MAX_EVENT_BYTES` (above every per-field limit, so only a bug reaches it). Before each write transaction the writer checks free space on the volume. Below `limits::MIN_FREE_DISK_BYTES` the store goes **read-only**: new turns are refused, running turns are interrupted, and the inbox shows a "storage full" item. Cleanup still works while read-only: signals, request expiry and final statuses, clearing a process, and batches made only of closing events. It recovers by itself when space returns.
- **Migrations** are numbered SQL files run in one transaction each, recorded in `schema_migrations`. A failed migration rolls back and the daemon refuses to start with a clear error; it never runs on a half-migrated database.
- **Snapshots.** `Store::snapshot` (M1-02) does `VACUUM INTO` a dated file in `Paths::snapshots_dir` (mode 0600) and keeps the last 7; the daemon (M1-05) calls it once a day when no turn is running.

## 8. Threads and attention (`atrium-core::attention`)

- `attention::next_state(current, pending, input) -> ThreadState` is a pure function, tested as a table. Inputs are stored events plus daemon signals (starting, exited, recovered with a cleanup result, storage read-only, user stop). The full transition rules are on `next_state`. In short: a user stop is `Ended` at once; `Failed`, `Ended` and `Interrupted` are sticky until the next start, and `Paused` through the closing events; otherwise exit code 0 ends as `Ended` and anything else as `Interrupted { cleanup: Verified }`.
- M1 states: `Starting`, `Running`, `NeedsApproval`, `NeedsInput`, `Idle`, `Paused { resets_at_ms }`, `Failed`, `Interrupted { cleanup }`, `Ended`. The M2 states (checks, review, merge) are added by a later revision.
- Inbox: one list across threads. Rank by reason (storage full > approval > question > failed > interrupted with unverified cleanup > unread reply), then oldest first by `ThreadSummary.attention_since_ms`; the card's text is `attention_detail`. The store keeps both fields up to date from events. `ThreadSummary.unread` is set by new assistant output (never by `User` messages) and cleared by `MarkRead`.
- Notifications: the daemon posts them (PLAN §3.4) for transitions into `NeedsApproval`, `NeedsInput` and `Failed`. They are grouped per thread, at most one per thread per `limits::NOTIFY_MIN_INTERVAL`, and suppressed while an App connection reports that thread as focused (`SetFocus`).

## 9. Policy (`atrium-core::policy`)

- **Home preset (M1's only location)**: *read freely, approve changes* (PLAN §3.3, D-050).
  - File reads and searches are allowed, except a recursive search rooted at `~` itself, which asks. That includes `rg` and recursive `grep` commands: they're auto-allowed only when every search root is given and is a file or a folder strictly inside `~` (`rg token` with no path searches all of home).
  - Commands in `HOME_READONLY_COMMANDS` are allowed, with their flag guards, when the line has no `$` expansion, globs, brace expansion or newline, no `git -c`/`--config-env`/`--exec-path`, no leading `NAME=value` assignment, and no redirect other than fd duplication or output to `/dev/null`. Everything else asks.
  - Known limit, shown in settings: a repository's own git config can run programs during git reads.
  - Codex: `sandbox=read-only`, `approval_policy=untrusted` (as verified in M0).
- **Subjects.** Adapters extract each call's `ToolSubject` (command line, paths, URL, MCP tool). Any shell command is `ToolKind::Execute` whatever the provider calls it. A subject the adapter can't extract is `Unknown`: it can only be hard-denied (on the raw input) or asked. `SessionGate` resolves paths (deepest existing ancestor canonicalized) and passes them in `PolicyInput`; the engine never touches the filesystem or environment.
- Presets `Careful`, `Normal`, `Trusted`, `FullAccess` exist as types; M1 uses Home's preset only, and workspaces pick presets in M2.
- **Rules** (`policy::Rule`): a tool kind, an optional tool name, a matcher (`CommandExact` on the whole argv, `CommandPrefix` on leading argv tokens, created only in the rules editor, or `PathGlob`), an optional path scope, a decision and a scope (thread / Home / global). Creating, editing and deleting rules is App-only.
- **Commands** are parsed with a POSIX shell-words parser; separators are `;`, `&&`, `||`, `|` and newline. A command rule (exact or prefix) matches only a simple command: no command or process substitution, backgrounding, `$` expansion, globs, leading `NAME=value` assignments, or redirects other than fd duplication and output to `/dev/null` (in any location: in Home the cwd is `~`, so "inside the cwd" would include `~/.zshrc`). A compound command is allowed by rules only if every segment is. Anything the parser can't handle asks. Hard-deny patterns are checked against every segment (looking through assignments), inside substitutions, and against the raw string.
- **Paths a command names.** `SessionGate` resolves every argument, flag value (`--flag=value`, `-Xvalue`), `key=value` operand, assignment value and redirect target, not only arguments that look like paths (`cat .npmrc` in Home names `~/.npmrc`). `cd`/`pushd` to a literal path, a bare `cd` and `cd -` move resolution for later segments; any other directory change makes the cwd unknown, so the line asks, relative paths are checked for hard deny against every cwd it could be, and a relative recursive delete is blocked. In Home's read-only list, `-f` (read names or patterns from a file) is forbidden for `file`, `rg` and `grep`, and flags that take a value never count as search roots. `redeem` re-resolves and always re-checks the hard-deny list, so a symlink swapped after the approval can't reach a blocked path.
- **Atrium's own paths** come to the engine in two sets: data (database, WAL, snapshots, logs), never read or written; and config, socket, service units and app, never written.
- **Hard-deny list**: `HARD_DENY_DEFAULTS` in `policy.rs`, approved by Pedro (D-050). It applies to every tool kind whose subject names a matching command or path, searches included. Changes need his approval (D-013).

## 10. Lifecycle and supervision

- `atriumd` (M1-05 server, M1-10 lifecycle):
  - The app connects and starts `atriumd` detached when it isn't running.
  - A lock file is taken before a stale socket is removed (as in M0).
  - "Keep agents running after quitting" installs a launchd LaunchAgent or a systemd user unit, and removes it when turned off.
  - Upgrades: an older daemon answers a newer app's `Hello` with `Incompatible { daemon_pid, daemon_version, running_turns }`. The app verifies that pid against the identity in the lock file, then sends `SIGTERM` (the daemon exits once no turn is running) or, after the user confirms, `SIGINT` (running turns are interrupted, resumable, and it exits now). A daemon of the same version takes `ShutdownDaemon` instead.
  - Logs are created mode 0600 with `O_NOFOLLOW`.
- **Process groups** (`atrium_host::supervise`, M1-10): every provider process starts in its own process group, and is reported through `SessionConfig::on_spawn` before the handshake so the daemon records it. Shutdown sends the provider's soft stop, waits `SHUTDOWN_GRACE`, `SIGKILL`s the **group**, then reaps the leader. An adapter never spawns a second provider process within one `Session`: if an interrupt needs a kill, the session ends and the daemon resumes it as a new incarnation.
- **Recovery** after a daemon crash verifies each recorded leader (start time + executable) before killing its group. A gone leader counts as cleaned up only if its group is empty too; if not, nothing is killed (the group id may have been reused). When identity can't be verified, the thread becomes `Interrupted { cleanup: Unverified }` and says so; it is never shown as stopped.
- **Terminal events under backpressure** (Claude finding): process cleanup is bounded by `SHUTDOWN_GRACE`, but closing events are not dropped. The adapter keeps a bounded terminal tail (`limits::TERMINAL_TAIL_EVENTS`) and delivers it when the receiver drains, or until the receiver is dropped.

## 11. Client and windows (`atrium-client`, `app/`)

- One `atrium-client` per app process: one socket connection, the only state authority in the app (D-028).
- Each window has its own delivery queue with a byte bound and its own applied cursor. A window that stops acknowledging (occluded, hung) loses its queue and is marked `needs_resync`; it resyncs from the client's state when it acknowledges again. It never stalls other windows or commands.
- Commands (approve, answer, interrupt) go through `invoke`, never through the event path.
- Forced close, crash and draft recovery are tested (gate review, multi-window).
- **Streaming memory.** A thread view keeps at most `limits::MAX_LOADED_TRANSCRIPT_BYTES` of rendered transcript; older parts leave the DOM and the virtualizer's state and are paged back from the client on scroll. M1-09b reports the WebContent peak during the §14 streaming run (M0-07 saw 1.05–1.39 GB).

### 11.1 UI tokens (CR-01 … CR-04, settled here)

- **CR-02 is accepted, with CR-01 folded in and CR-04's amendments.** Runtime window tokens (`--window-alpha-chrome`, `--window-alpha-content`, `--window-opacity`, `--window-blur`) are set by the app, never by a theme; a theme defining one is a load error. The loader emits `--<surface>-rgb` channel tokens for `surface-0`, `surface-1`, `surface-2` and `surface-overlay`; theme surfaces are six-digit opaque hex, and the `-rgb` names are reserved. `surface-glass` stays for always-translucent overlays. New required semantic tokens: `--hover`, `--selected`, `--state-needs-you-bg`, `--state-failed-bg`, `--state-ready-bg`, `--state-running-bg`, `--shadow-overlay`, `--scrim`, `--glass-blur`, and `--syntax-*` (filled from `tokenColors` by the VS Code importer). The contrast check adds the four state colours as text on `surface-0..2`.
- Whole-window opacity is the native window alpha (`NSWindow.alphaValue`), not CSS `opacity`. Layout B's component tokens (`advanced-width`, `panel-width-editor`, the sidebar and panel drag bounds) belong to the Calm themes. Atrium observes the OS accessibility display options and repaints every window when they change.
- **Blur strength** applies only to in-window overlays (palette, popovers). Its settings note says so, per platform: on macOS "macOS sets the window's blur; this only affects overlays", and on Linux "Atrium uses opaque windows on Linux" (L1).

## 12. Rendered agent content

Agent text is untrusted input.
- Markdown renders to DOM nodes, never through `innerHTML` of model text. Raw HTML in markdown is shown as text.
- Links: `http`, `https` and `mailto` only, opened in the system browser after one click, with the full URL shown on hover. `file:` links are resolved (symlinks included); a path inside the thread's cwd is revealed in the file manager (or Atrium's preview in M2), never opened or executed. Anything else is plain text.
- Images: `data:` raster images (png, jpeg, gif, webp) up to `limits::MAX_INLINE_IMAGE_BYTES` render; SVG never renders inline. Remote images don't load until clicked (privacy), then load with `referrerpolicy="no-referrer"` and no cookies.
- No agent-controlled string ever selects a Tauri command, a window label or a capability. The app's CSP: `default-src 'self'; img-src 'self' data: https:; connect-src ipc: http://ipc.localhost; script-src 'self'; style-src 'self' 'unsafe-inline'` (the remote `img-src` is only used after the click).

## 13. History basics

- Every thread stores its provider's native session id per incarnation (`sessions` table), so resume and export can name it.
- Export (M1-11): one thread to Markdown or JSONL. Messages are reconstructed from deltas and verified (§6.1). Secrets are redacted with `history::Redactor`, on decoded and reconstructed content (escapes and nested JSON included, A12/A13), using common token patterns since real sessions have no known canaries. The home directory becomes `~`; the user name is kept. Files are created by `history::create_export_file` (new file only, mode 0600, `O_NOFOLLOW`). User messages are exported and redacted like the rest.
- `SessionConfig`, `McpServer` and every type holding env values or args print redacted in `Debug` (done in the contract).
