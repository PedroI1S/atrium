## 3. Adapter requirements (M0-01 … M0-04)

### 3.1 Policy enforcement
- Every tool call the adapter can intercept goes through `SessionConfig::gate` **before it runs**. A gate or hook failure of any kind denies the call (fail closed).
- `interception()` returns `AllToolCalls` only if that holds for every tool class, MCP tools included; otherwise `ProviderGated`.
- Every spike report has an **enforcement matrix**: rows = tool classes (read, edit/write, delete/move, execute, search, fetch/web, MCP, subagents, anything provider-specific); columns = *intercepted before execution?* (yes / no / partial), *how* (hook, control request, JSON-RPC server request, client capability), and *evidence* (the fixture or test that shows it).
- Every `PermissionPolicy` works on every transport, including `FullAccess` on the host: safe modes are the defaults, but the user decides (D-011). In `FullAccess` the gate is still called wherever the adapter can intercept, and applies whatever rules the user has set.

### 3.2 Lifecycle and backpressure
- Follow the lifecycles in `atrium_protocol::agent` (established session vs pre-session failure; closing order on exit).
- **Saturation test** (required): a session whose event receiver is never read still obeys `Interrupt` and `Shutdown` within `SHUTDOWN_GRACE`, the child is reaped, and no thread or task is left behind.

### 3.3 Fixtures
- Format and golden tests: `crates/atrium-agents/src/fixture.rs`. Files: `fixtures/agents/<provider>/<scenario>.{jsonl,events.json,md}`. A fixture records **every** `AdapterInput` (stdin, stdout, stderr, hook traffic, gate decisions, client commands, exit), and live sessions run through the same `Normalizer`.
- **Required scenarios per adapter**, each a golden test:
  1. `simple`: a one-line answer, no tools.
  2. `tool-read`: the agent reads a file; the gate allows it.
  3. `gate-deny`: the agent is asked to read `secret.txt` in the scratch dir; the gate denies it and the file's contents never appear in any event. This is the proof for the enforcement matrix's read row; do the same for execute.
  4. `approval-allow` and `approval-deny`: a command the gate answers `Ask`, resolved both ways, each ending in `RequestResolved`.
  5. `question`: the agent asks a multiple-choice question, answered with structured answers (skip if the provider can't ask; say so).
  6. `interrupt`: `Interrupt` mid-tool-call; the turn ends `interrupted` and open calls end `cancelled`.
  7. `multi-turn`: two user messages in one session.
  8. `resume`: a second process resumes the first session by native id.
  9. `startup-error`: an invalid model id (or the provider's equivalent); pre-session lifecycle, no `SessionStarted`.
- Every committed fixture goes through `Sanitizer` (decoded values, secrets first) and `Sanitizer::is_clean` is asserted on the written file. Use the cheapest model the provider offers. Each `.md` says `live` or `hand-made`.
- A worker who can't run the provider CLI in its own sandbox writes the live harness (`cargo run -p <crate> --example record -- <scenario>`) and hand-made fixtures from the provider's documented schema, says so in the handoff, and the orchestrator records the real fixtures during verification.

## 4. UI tokens (M0-06 implements, the M1 app inherits)

PLAN §3.20. Three layers, all CSS custom properties, set at runtime on `:root`:

1. **Primitive**: `--p-<palette>-<step>` (e.g. `--p-gray-50 … --p-gray-950`, `--p-accent-500`), `--p-space-<n>`, `--p-radius-<n>`, `--p-font-<role>`, `--p-text-<size>`, `--p-duration-<speed>`.
2. **Semantic** (components use only these and layer 3). Required set; a theme that misses one fails validation:
   - surfaces: `--surface-0` (window), `--surface-1` (panels), `--surface-2` (raised), `--surface-overlay`, `--surface-glass` (vibrancy panels, with alpha)
   - text: `--text`, `--text-muted`, `--text-faint`, `--text-on-accent`
   - lines: `--border`, `--border-strong`, `--focus-ring`
   - accent + states: `--accent`, `--accent-hover`, `--accent-muted`, `--danger`, `--warning`, `--success`, `--info`
   - code and diffs: `--code-bg`, `--diff-add`, `--diff-del`, `--diff-add-text`, `--diff-del-text`, `--ghost-text`
   - attention states (§3.4): `--state-running`, `--state-needs-you`, `--state-failed`, `--state-ready`
   - density and motion: `--space-unit`, `--radius`, `--font-ui`, `--font-code`, `--text-ui`, `--text-code`, `--motion-fast`, `--motion-normal`
3. **Component**: `--<component>-<property>`, e.g. `--tab-active-bg`, `--composer-radius`, `--sidebar-width`. Defaulted from semantic tokens in the component's CSS; a theme may override them.

**Theme file** `themes/<name>.toml`:

```toml
[meta]
name = "Atrium Dark"
appearance = "dark"            # dark | light
vibrancy = true                # use --surface-glass + native blur where available

[primitive]
gray-50 = "#f7f7f8"            # → --p-gray-50
# …

[semantic]
surface-0 = "{gray-950}"       # "{name}" references a primitive
accent = "#7c8cff"             # or a literal
# …

[component]                    # optional overrides
tab-active-bg = "{surface-2}"
```

- References resolve primitive → semantic → component; a cycle or a missing reference is a load error.
- Switching themes replaces the variables in place, with no reload. The loader validates the required semantic set and checks WCAG AA contrast for `--text`/`--text-muted` on `--surface-0..2` and `--text-on-accent` on `--accent`.
- VS Code import maps `colors` → semantic tokens. The mapping table is part of the M0-06 report; Shiki/CodeMirror themes come from `tokenColors`.

## 5. Measurements

- Budgets are PLAN §4. Every number in a report says how it was measured and gives the exact command to reproduce it.
- **Cold start** means *time to interactive*: from process launch until the window has painted **and** the first input (a keystroke in the composer, or a palette open) is handled. First paint is reported separately.
- **Linux / WebKitGTK**: not measured on this machine. Each UI spike lists exactly what a Linux run must check. The deferral, its owner and the gate it must be done by are a driver decision (recorded in `decisions.md` when made).

## 6. Spike reports

Every spike ends with `docs/spikes/<task-id>.md`: what was built, measurements (§5), what broke, the enforcement matrix (adapters), a recommendation for M1, and open risks. The handoff note links to it.
